# 任务拆分方法论 skill — 正交分解 + 加桩并行 + 约束优先

## When to use

- 手上有一批需求（产品需求 + 开发需求），要拆成任务 / 工作包，分给多人/多团队
- 要看"哪些能并行"、画并行线、做需求↔任务映射、定提测节点
- 要评估一份已有的拆分"合不合理"（覆盖全不全、多对多正不正常、约束在哪）
- 多团队 / 多仓库 / 跨职能（C++ + FE + 算法）协作的项目规划

**不用的场景**：单人单模块的小任务（直接做）、纯执行无规划余地、需求本身没定（先去澄清需求）。

## 核心原则（先建立这个心智模型）

**线和需求是两个正交的分解轴，规划的本质是处理这张矩阵。**

| | 切分依据 | 回答 |
|---|---|---|
| **线（task-line）** | 技术模块 / 代码归属 / owner | "怎么建、谁写代码" |
| **需求（requirement）** | 用户可见能力 | "交付什么价值" |

两个正交轴交叉 → 必然得到一个**矩阵**，矩阵一般**非块对角** → **多对多是结构必然，不是规划失误**。
- 叶子功能 → 1 条线（1:1）
- 集成型需求 → 天然跨多条线（多对多）= 集成/联调风险地图，信息量最高

这套形式化在学术上叫 **DSM（Design Structure Matrix）/ MDM（多域矩阵）**：任务×任务、需求×线、团队×模块都是同一张大矩阵的切片。

## Workflow（8 步）

### 1. 两套独立分解：先列"线"，再列"需求"

- **线**：按技术模块切，目标**高内聚、低耦合**（Constantine/Yourdon）；模块边界按"最可能独立变化的设计决策"划（Parnas 信息隐藏）。每条线一个主 owner。
- **需求**：按用户能力列全。**遵守 WBS 100% 规则**——拆出的工作必须覆盖 100% 的交付物、子项互斥（不重不漏）。区分**产品需求**（用户可见）与**开发需求**（工程建造，如"新增 X 模块"），后者常是多条线的共同归属行。

### 2. 做需求×线映射矩阵（DMM）+ 覆盖核对

把每个需求归并到线上，列一张**需求→线**表。然后**反向核对全覆盖**：
- 每个需求是否 ≥ 1 条线？（无孤儿需求）
- 报一个明确的覆盖数：`N 个在范围需求 + M 个开发需求 = X 行全部落位；K 行出范围已隔离`
- 出范围/纯前端等不占后端线的，**显式单列**，别混进来制造假覆盖

### 3. 识别多对多 → 每个集成型需求钦定"主责线 + 集成 owner"

跨多条线的需求 = 集成型需求。**健康的关键不是消除多对多，而是给每个多线需求钦定唯一收口人**（single-threaded owner，Amazon 式"一个人对结果负责"）。列一张表：

| 多线需求 | 跨线 | 主责线 | 集成 owner | 供料方 |

### 4. 识别"使能线" → 显式标注不独立验收

某条线若**从不单独拥有一个用户可见需求**，永远是别人的子件（典型：底层算法库、运动学、平台能力）——它是**使能线**（Team Topologies 的 complicated-subsystem / enabling team）。
- 标记为〔使能线〕
- 它的"完成度"通过它供料的集成需求间接验证，**不独立提测**
- 但它若是外部交付（如第三方算法 dll），**单独保留交付节点**，别因为归进某个集成需求就把外部 deadline 看丢

### 5. 找跨线依赖 → 加桩解耦（DSM tearing）

把"B 线等 A 线真实现"的串行依赖，用桩改造成并行：
1. **先冻结接口契约**（这是前提，必须准时）
2. A 出**桩**（返回固定假数据的 stub/fake，术语来自 Meszaros 的 test double）
3. B 拿桩**并行开工**，搭自己的流程/框架
4. A 真实现好 → **替桩 + 联调验证**

桩=DSM 里"撕开反馈环"+ 依赖倒置。⚠️ **桩只验流程联通，不验正确性**——替真后必须联调验证。

### 6. 识别真约束（TOC）→ 通常是人力不是技术依赖

**加桩解开的是"等接口"的技术依赖；但人手决定真实现的先后。** 用约束理论（Goldratt）走一遍：
- **识别约束**：往往是 headcount（N 个人满载），不是技术依赖
- **exploit（榨干约束）**：保证瓶颈人**零浪费**——别让瓶颈人做非瓶颈也能做的事。⚠️ 检查集成 owner 是否过度集中在一个人（见步骤 3 表），过载就把能外移的收口移走
- **subordinate（一切服从约束）**：非瓶颈资源配合瓶颈节奏
- 诚实结论：**stub 提高并行度，但不增加总人力、不缩短总工时**

### 7. 排期 + buffer（关键链思路）

- 关键路径/关键链照常算
- buffer **别"每个节点各拍一点"**；关键链 CCPM 的做法是砍掉每任务安全余量、**集中成一个项目缓冲**，用**缓冲消耗率**做单一健康指标——更省、可度量、好向上汇报
- 重要节点/新人/外部依赖处适当加保护

### 8. 维护 SSOT（防数字漂移）

- 设一个**数字 SSOT**（manifest：task 数/工时/编号/里程碑）和一个**规划活记录 SSOT**（wiki 或活文档）
- **改动顺序**：先改 SSOT 数字源 → 再改 detail 文档 → 后 sweep 摘要文档
- 禁止跳过 SSOT 直接改摘要，禁止 detail 与 SSOT 打架

## 健康判据（验收一份拆分用这 3 条，不是"1:1 映射"）

1. **覆盖性**：每个需求 ≥ 1 条线，无孤儿需求
2. **主责性**：每个多线需求有唯一主责线 + 集成 owner
3. **可交付性**：每条主线能独立提测 ≥ 1 个完整单元；纯使能线显式标注不独立验收

## 3 种真异常（多对多本身不是异常，这 3 个才是）

| 形态 | 为什么异常 | 修复 |
|---|---|---|
| 跨多线但**无主责 owner** | 集成无人兜底，需求从缝里掉 | 钦定主责线 + 集成 owner |
| 两线对**同一子部分**都负责 | 职责重叠、边界不清 | 按子部分切给线，写清边界 |
| 某线**从不独立交付完整需求** | 它不是可并行的线，是依赖项 | 标为使能线，随集成需求验证 |

## 粒度原则（重要，常见踩坑）

**给开发含冗余量的工作包，让他自己拆分规划——不要替他切到 0.25d 微任务。**
- 工作包粒度宁可粗（含 buffer），开发是成年人，自主拆解
- 过细的拆分=虚假的精确 + 维护成本爆炸 + 剥夺开发判断
- 拆到"知道改哪个模块、谁负责、什么时候提测"即可，再细就过了

## 反模式（别做）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 追求"线 1:1 映射需求" | 正交轴注定非双射，做不到 | 用覆盖性 + 主责性判健康 |
| 把多对多当 bug 去消除 | 等于假装集成需求不存在 | 多对多正常，钦定集成 owner 收口 |
| 加桩=以为能凭空并行真做 | 桩解技术依赖，没解人力约束 | 走 TOC 识别真瓶颈 |
| 桩替真后不联调 | 桩只验流程不验正确性 | 替真必联调验证 |
| 集成收口全压一个人 | 违反 TOC exploit、单点风险 | 检查 owner 集中度，外移可移的 |
| 拆到 0.25d 微任务 | 虚假精确 + 剥夺开发判断 | 含冗余工作包，开发自拆 |
| 改摘要不改 SSOT | 数字漂移、文档打架 | 先 SSOT 后 detail 后摘要 |
| 外部依赖归进集成需求后丢了它的 deadline | 最易延期的外部交付失管 | 使能/外部线单独保留交付节点 |

## 理论索引（要向人解释"为什么这么拆"时引用）

| 实践 | 理论 | 一句话 |
|---|---|---|
| 统一框架 | **DSM / MDM**（Eppinger & Browning 2012）| 任务/需求/团队都是同一张矩阵的切片 |
| 覆盖核对 | **WBS 100% 规则**（PMI）| 不重不漏 100% 工作 |
| 模块边界 | **Parnas 信息隐藏**（1972）| 按变化决策切、接口藏实现 |
| 多对多映射 | **DMM 域映射矩阵**（Danilovic & Browning 2007）| 两域映射本就是矩形矩阵，多对多是定义 |
| 线/需求错位 | **康威定律**（1968）| 组件团队 vs 特性团队张力 |
| 加桩 | **DSM tearing + test double**（Meszaros 2007）| 撕反馈环 + 依赖倒置 |
| 真约束 | **TOC 约束理论**（Goldratt）| 产出由瓶颈定、服从约束 |
| buffer | **关键链 CCPM**（Goldratt）| 集中项目缓冲 + 消耗率 |
| 使能线/集成 owner | **Team Topologies**（2019）| complicated-subsystem / single-threaded owner |

延伸阅读：Eppinger《DSM Methods and Applications》/ Goldratt《Critical Chain》/ Skelton & Pais《Team Topologies》/ Parnas 1972 论文（15 页）。

## Worked example（首个真实案例：智能焊接 v2）

- 6 C++ + 3 FE + 外部算法团队，~137d，7 条并行线（焊缝几何/拾取/路径规划+碰撞/运动学/设备管理器/工艺自匹配/算法dll）
- 需求×线 DMM：34 行全覆盖；叶子功能（拾取→②、自匹配→⑥）1:1，集成型（姿态预估/工艺仿真/自动规划）跨 3-5 线
- ④运动学、⑦算法dll = 使能线，归进开发需求"算法模块"（= WeldPlanningAdapter）
- 8 个桩解耦跨线依赖（接口契约/Mock dll/KDL stub/Mock BE/IWeldDomain 桩…）
- 真约束 = 6 人 headcount；发现 6 个集成 owner 里 4 个压在核心工程师 → TOC exploit 提示外移
- 详见 `E:\分析\智能焊接\S13-任务拆分-v2\40-项目管理\`（05 映射 / 06 桩 / 方法论依据.md）
